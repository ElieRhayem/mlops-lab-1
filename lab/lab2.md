## Question 2

### What are `--backend-store-uri` and `--default-artifact-root` used for?

The MLflow tracking server was started using:

```bash
uv run mlflow server --host 127.0.0.1 --port 5000 --backend-store-uri sqlite:///mlflow.db --default-artifact-root ./mlruns
```

`--backend-store-uri` determines where MLflow stores experiment and run metadata.

In this lab, the backend is:

```text
sqlite:///mlflow.db
```

Therefore MLflow stores the tracking metadata in the local SQLite database `mlflow.db`.

Examples of metadata include:

- experiments
- run IDs
- parameters
- metrics
- tags
- timestamps
- run status

`--default-artifact-root` specifies the default artifact storage location for experiments created by the tracking server configuration.

In this lab it is configured as:

```text
./mlruns
```

Artifacts are larger files associated with a run rather than scalar tracking metadata. Examples include trained models and model-related files.

Therefore the main distinction is:

**Metadata** describes the experiment and its results, while **artifacts** are the actual files produced by an experiment.

For example, the value of `val_accuracy` is metadata, while the serialized trained ResNet18 model is an artifact.

## Question 3

### Why should `mlflow.db` and `mlruns/` not be tracked by Git or DVC?

`mlflow.db` and the MLflow artifact directories are generated experiment outputs rather than source code.

`mlflow.db` changes whenever experiments and runs are created or updated. Tracking the database using Git would produce unnecessary binary changes and would not provide a useful source-code history.

The artifact storage can also contain relatively large model files generated by each training run, so these files should not be stored in the Git repository.

They also do not need to be managed by DVC in this lab because MLflow already provides the experiment-tracking and artifact-management functionality for these outputs.

The responsibilities are therefore separated as follows:

```text
Git    -> source code and project configuration
DVC    -> dataset versions
MLflow -> experiment runs, parameters, metrics, and model artifacts
```

For this reason, the local MLflow outputs were added to `.gitignore`.

## Question 4

### What happens the first time `mlflow.set_experiment("food11")` is called?

The training script contains:

```python
mlflow.set_tracking_uri("http://127.0.0.1:5000")
mlflow.set_experiment("food11")
```

The first time `mlflow.set_experiment("food11")` is called, MLflow checks whether an experiment with that name already exists.

Because it does not yet exist, MLflow creates a new experiment named `food11` and makes it the active experiment.

After the first training execution, the `food11` experiment became visible in the MLflow web interface.

Subsequent runs using the same experiment name were added under the existing `food11` experiment rather than creating another experiment.

## Question 5

### What is the difference between `mlflow.log_param` and `mlflow.log_metric`?

A parameter represents a value selected before or at the beginning of training that remains fixed for a particular run.

Examples include:

```text
learning rate
batch size
number of epochs
dataset
model architecture
```

These were logged using `mlflow.log_param()` or `mlflow.log_params()`.

A metric represents a numerical result produced during or after the training process.

Examples in this lab include:

```text
train_loss
val_loss
val_accuracy
test_accuracy
```

Metrics may change as training progresses.

For example, validation accuracy may have a different value after every epoch.

For this reason, `mlflow.log_metric()` accepts a `step` argument. In this lab the step represents the epoch number:

```python
mlflow.log_metric(
    "val_accuracy",
    val_accuracy,
    step=epoch,
)
```

This allows MLflow to store the history of the metric and plot how it changes from epoch to epoch.

Parameters do not need a `step` because their values remain fixed for the entire run.

## Question 7

### Which learning rate gave the best `val_accuracy`? Is higher always better?

For the runs using `batch_size = 32`, I observed:

```text
lr = 0.01
val_accuracy = 0.19160583941605838

lr = 0.001
val_accuracy = 0.6012773722627737

lr = 0.0001
val_accuracy = 0.7226277372262774
```

The learning rate that produced the highest validation accuracy was:

```text
lr = 0.0001
```

with a validation accuracy of:

```text
val_accuracy = 0.7226277372262774
```

A higher learning rate was not necessarily better. The learning rate controls the size of the optimizer updates. A value that is too large can make optimization unstable or cause the model to move past useful minima, while a value that is too small can result in slower learning during the limited number of epochs.

The experiment therefore demonstrates that learning rate should be treated as a hyperparameter to evaluate rather than a value for which larger automatically means better.
